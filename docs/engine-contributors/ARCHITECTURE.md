# Architecture notes

Why the engine is shaped as it is, module by module. `CLAUDE.md` states the
rules; this gives the reasons, so a change can tell a load-bearing choice from
an incidental one. Engine operations are named by their entry in the operation
table; each is reachable as `/engine/<name>`, as an MCP tool and through
`engine.call`.

## Request lifecycle

1. `main.rs` loads config (`config::AppConfig`), sets up tracing, then calls `start_server_with_config` in `lib.rs`.
2. `lib.rs::initialize_components` brings up the database (`database.rs`, which applies pending migrations), the repository (`repository/`, one file per topic — the source of truth for scripts, files, logs, secrets and script metadata), `notifications.rs` (Postgres LISTEN/NOTIFY, keeping a cluster's caches in sync), the `scheduler` module, and the engine's own streams (`engine_api::register_engine_streams`).
3. Every script is executed once at startup (`execute_startup_scripts`), in name order, then each script's `init()` is invoked (`script_init.rs`) to populate route, MCP and scheduler registrations.
4. A request that matches no static Axum route is matched against script registrations: `find_route_handler` in `lib.rs` reads the route index, scored by specificity (exact > `:param` > `/*`).
5. A matched request is dispatched into `js_engine::execute_script_secure` (or a streaming variant), which creates a QuickJS `Runtime`/`Context`, installs the sandboxed globals, builds the script via `module_loader.rs` + `transpiler.rs` (TS/JSX → JS with `oxc`), and runs the named handler with a per-request `UserContext`.

## Security sandbox model

- Every JS global goes through `security::secure_globals` (one file per global). That is the enforcement point, not `js_engine`.
- Authorization is by capability (`security::capabilities::Capability` + `UserContext`), never by role string. `UserContext::anonymous()/authenticated()/editor()/admin()` map to fixed capability sets built from the user's roles. Anonymous callers read scripts and files and change nothing, and no mode widens that: administering an engine takes being an administrator (`auth.bootstrap_admins`, `auth.internal.bootstrap_admin_usernames`, or `--grant-role` with no server running). Tests sign in as a fixed administrator through `tests/common`'s `AdminServer`, so the engine APIs are exercised through the middleware a deployment runs.
- Half the capability enum names what a person may do to a solution and half names what a _script_ does while it runs — `UseNetwork`, `ReadSecrets`/`WriteSecrets`, `ReadStorage`/`WriteStorage`, `EnqueueTasks`, `ReadScriptData`/`WriteScriptData`. Reads and writes of a script's tables are separate names so that a read-only execution is expressible. Every tier that can do the thing holds the name for it — the anonymous tier included, since a signed-out visitor's request may `fetch` — so the second half exists to be taken away by `UserContext::attenuated`, not to gate tiers.
- The four tiers are distinct on purpose. **Authenticated** is someone _using_ a solution: a script serving a request runs as the requesting user, so this tier holds what an ordinary request needs (`ReadScripts`, `ReadAssets`, `ViewLogs`, `ManageStreams`, `ReadScriptData`, `WriteScriptData`) and nothing that edits the solution. **Editor** adds authoring (`WriteScripts`, `DeleteScripts`, `WriteAssets`, `DeleteAssets`, `DeleteLogs`, `ManageMcp`, `ManageScriptDatabase`), always paired with an ownership check. **Administrator** adds `AdministerEngine`, the marker for acting on what you do not own — never test `DeleteScripts` as a proxy for "is an admin".
- **What narrows what** — role, realm, token audience, session elevation, delegation, `sandbox.run` and script limits — is one page: `docs/WHAT_NARROWS_WHAT.md`. The authority-narrowing ones all go through `UserContext::attenuated`, an intersection that only takes away, never changes who is acting, and refuses at the call rather than narrowing silently.
- All scripts are equal. Every script sees the same JS API, and each call is authorized against the _calling user_: their capabilities, whether they own the target script (`script_owners`, `repository::user_owns_script`), and their roles (`user_repository::UserRole`). Engine administration is not a JS global; it is the operation table, where `engine_api` applies the same capability, ownership and administrator rules.
- `security/headers.rs` applies `security.enable_security_headers` and `security.content_security_policy`. It sets `X-Content-Type-Options`, `Referrer-Policy` and (over HTTPS only) `Strict-Transport-Security` on every response, and the configured CSP only on engine-owned paths (`engine_api::RESERVED_ROUTE_PREFIXES`): a policy describes how a page is built and the engine can speak only for pages it wrote, so script responses set their own. It never replaces a header the response already carries. Engine pages with inline `<style>`/`<script>` set their own nonce policy first (`security::engine_page_policy`).
- `security/cors.rs` draws the same line for CORS, for the same reason. `security.cors_allowed_origins` applies to engine-owned paths only; script routes set their own headers, since a solution knows which callers it wants. The default is empty (same-origin only) so that nothing reads `/engine/*` cross-origin unless an operator says so. Origins are matched exactly after lower-casing and dropping a trailing slash, because a prefix match would admit `https://example.com.attacker.test`; anything that is not an origin — a URL with a path, an unexpanded `${VAR}` — is dropped at startup with a warning. A named origin gets `Access-Control-Allow-Credentials: true` and `"*"` does not: reflecting an arbitrary origin _and_ allowing credentials would let every site a signed-in administrator visits read `/engine/*` as them. The layer answers preflights itself — an `OPTIONS` reaching a `POST`-only handler is a 405 the browser reports as a CORS failure — and sits outside anything that wants a session, since a preflight carries no credentials. It never replaces a header already present, which is how the OAuth2 endpoints keep the wide policy browser-based MCP clients need.
- `security/client_ip.rs` establishes the request's address once, at the edge. `X-Forwarded-For` and `X-Real-IP` are read only when the connection came from a proxy in `server.trusted_proxies` (empty by default, so nothing is believed), and the chain is walked right-to-left to the first untrusted hop, because the leftmost entry is written by the client. `normalize_client_ip` is the outermost layer bar security headers: it rewrites the forwarding headers to the single surviving address, so middleware, handlers and scripts all read one judged value through `client_ip::from_headers`. The socket address comes from `ConnectInfo` (`into_make_service_with_connect_info`). The shipped Caddyfile sets `header_up X-Forwarded-For {remote_host}` so the proxy overwrites rather than appends.
- `security/cross_origin.rs` refuses a signed-in state-changing request from another origin.
- Other `security/` modules: `csrf.rs`, `encryption.rs` (AES-GCM, for sessions and at-rest secrets), `rate_limiting.rs`, `session.rs`, `elevation.rs`, `audit.rs`, `script_crypto.rs`, `threat_detection.rs`, `validation.rs`, `csp.rs`. The whole directory is security-critical (`SECURITY.md`).

## A script is one tree

- A script's files are rows of `assets` keyed `(script_uri, path)`, and its **entrypoint is one of them**: the file named `main.{ts,js,tsx,jsx}` (`module_loader::ROOT_MODULE_NAMES`, in that resolution order). `scripts` holds identity, display name, ownership and init status, and no content. One storage shape means one implementation of every read, write, patch, listing, history and git surface, with no "and also the root" special case.
- The entrypoint's name comes from the tree. `SourceView::root_path` asks whichever view is in play — stored rows, a revision's manifest, or an overlay — so renaming `main.ts` to `main.js` is how an author says the entrypoint is not TypeScript. A script with no files yet takes its default from `module_loader::default_root_module_name`.
- One storage shape does **not** mean one permission. Writing a `main.*` takes `WriteScripts` and ownership by every route in — `write_file`, `write_files`, `edit_file`, git pull — and removing one takes `DeleteScripts`, because otherwise what a holder of `WriteAssets` could not overwrite they could delete. The entrypoint keeps a 1MB ceiling (`MAX_SCRIPT_CONTENT_BYTES`) rather than the 10MB file one.
- `repository::invalidate_script_asset_caches` is where a write to the entrypoint becomes a change to what is _running_: the metadata cache holds the root source and every execution path reads it from there. It refreshes that entry in place (eviction would also drop the script's route registrations and 404 every route until re-init finished) and skips a pinned script, whose deployment is a revision rather than head.
- The file operations are one set keyed `(script, path)` — `read_file`, `write_file`, `write_files`, `edit_file`, `create_file`, `delete_file`, `list_files`, `search_files` — beside the script-level `list_scripts` and `delete_script`. Underneath, `read_file_authorized`, `write_file_bytes_authorized` and `patch_file_authorized` are one implementation each and decide policy from the path. A whole read answers `encoding: "utf8"` with text and `encoding: "base64"` otherwise.
- A script reaches its own tree through the `files` global (`list`, `read`, `write`, `delete`, by path; `assets/files_prelude.js`): a read is text or `null`, binary is asked for with `{ encoding: "base64" }`, and failures throw. Unlike the other globals it is configurable and writable, so a script's own top-level `const files` shadows it rather than being a `SyntaxError`. It refuses to write or delete a `main.*`, so it cannot hand a script its own program.

## JavaScript-facing API surface

- There are no built-in engine scripts. Everything the engine can be asked to do is one entry in `engine_api::native_tools` — a name, a description, a JSON schema and a function over `(&Value, &UserContext)` — and three things read that table: `/mcp` `tools/call`, `engine.call` from JavaScript, and `src/engine_http.rs`, which publishes every entry as `POST /engine/{name}` (JSON body) and, for the names in `READ_ONLY`, `GET /engine/{name}?arg=...` (query values read against the schema's types). `/engine/openapi.json` is rendered from the same schemas (`engine_http::openapi_paths`), so the HTTP surface, the MCP surface and the document cannot disagree about an argument. A refusal is an `engine_api::Refusal` with a kind, and `engine_http::status_of` is the one place that turns it into 400/403/404/409/500; a `{ "ok": false, ... }` report (a snippet that threw, a check that found a problem) is an answer and stays 200. `management_hosts` is enforced once, on the router `engine_http::router()` is merged into.
- Hand-written, because they are not operations: the SSE log tail (`/engine/script_logs/stream`) and update stream (`/engine/script_updates`), the cluster probe (`/engine/health/cluster`, whose 503 is its answer), `/engine/installed`, `/engine/openapi.json`, `/engine/engine.css`, `/auth/unauthorized` and `/favicon.ico` (`src/engine_api/pages.rs` and `lib.rs`). Engine assets (favicon, type definitions) are compiled into the binary and served by the static-asset fallback in `repository::fetch_asset`. Ad hoc test fixtures live in `scripts/test_scripts/`; example solutions live in `aiwebengine-examples`.
- The JS API's types are served at `/engine/types/v{version}/aiwebengine.d.ts`; `engine.call` argument types are generated from the operation table (`engine_types.rs`). `make typecheck` validates `scripts/**` against `assets/*.d.ts`.
- `module_loader.rs` is a minimal CommonJS-like bundler for a script's imports (no dynamic `import()`); `transpiler.rs` handles TS/JSX/TSX with `oxc`. `ModuleKind` sorts a module into code, JSON or text before anything reads it: `.md` and `.txt` are string modules whose default export is their content, so a system prompt is `import policy from "./skills/refund.md"` — resolved at link time, cached in the prepared program, dropped on write and pinned by the revision. The sort comes first because a data module's bytes are content: transforming one as code would turn a string that reads like an import into a dependency.

## Multi-host serving

- `server.base_url` names the default host; `server.additional_base_urls` adds more. `hosts.rs` resolves a request's Host header onto one of them, falling back to the default for anything unrecognised (direct IP, dev machine, tunnel), so single-host deployments are unaffected.
- `server.management_hosts` restricts the management surface to the listed hosts; empty means all. It covers every `/engine/*` endpoint except the static `/engine/installed`, and the engine's native MCP tools on `/mcp`. Enforced in three places: a layer on the management router in `lib.rs`, a `/engine/` prefix check in `handle_dynamic_request` covering the `/engine/script_updates` stream, and the `native_allowed` flag in `mcp::list_tools_for_host` / `tool_is_available_on_host`. It is matched against the raw Host header, since a management host need not be a host scripts publish on.
- A script's registrations are published on the default host unless `script_hosts` binds it elsewhere; a `*` row means every configured host. Administrators change bindings with `get_script_hosts` / `set_script_hosts`.
- The route index is keyed `(host, path, method)`, so two scripts can claim the same path on different hosts. Everything else filters through `route_index::script_serves_host` / `scripts_for_host`, which share the index's cache and invalidation.

## Other core modules

- `mcp.rs` / `mcp_client.rs`: the JSON-RPC 2.0 Model Context Protocol endpoint (`/mcp`), as a server (script-registered tools, prompts and resources) and a client (`McpClient`, for scripts calling other servers). The server is dual-era: a request carrying `io.modelcontextprotocol/protocolVersion` in `_meta` is served statelessly under `2026-07-28`, and an `initialize` handshake selects a legacy revision.
  - **Resources** are the read half: `mcpRegistry.registerResource` publishes a file from the script's `resources/` under a URI. A resource is file-backed rather than handler-backed because a resource whose content came from a handler would be a tool with a different spelling, answering differently every time, which a client caching by URI does not expect; a file changes only when somebody writes it and `revisions.rs` records that they did. It is read at `resources/read` rather than copied at registration, so a rewrite reaches clients without a redeploy. `resources/read` decides `text` against `blob` by whether the bytes are text, not by the declared MIME type. Listing and reading filter by host, and a URI published elsewhere is refused identically to one that does not exist, so URIs cannot enumerate other hosts.
  - **Tasks** (`mcp_tasks.rs`, the `io.modelcontextprotocol/tasks` extension): a handler calls `mcp.task` and the call ends with a `CreateTaskResult` the client polls. The _script_ decides, because by the time the engine could measure that a handler is slow the handler has started. `mcp_tasks` is a table of its own rather than columns on `script_tasks` because their lifetimes are opposite: the queue deletes a row on success, while an MCP task's completed row is the one that must survive until the client reads it. The handler's return value is the task's result, wrapped at read time in the envelope a synchronous call would have produced, so a client never branches on whether its work was queued. One attempt, because a retried tool call is a second run of work the client was told had started; script context rather than the caller's, because an MCP client holding a token is not a person consenting to background work. A handle is given only to a client that declared the extension per request, and so never to a legacy client (which has no `_meta`). `input_required` is representable and unreachable, so `tasks/update` acknowledges and ignores. Handles expire after an hour.
  - **Authentication**: `/mcp` takes only a Bearer token whose audience names the host and path requested (`security::session::resources_match`). A browser login carries no audience, so a session cookie is not an API credential — a bearer header discards the host scoping a cookie relies on. A client builds the protected-resource document's URL from the MCP server's URL (RFC 9728 §3.1), so `/.well-known/oauth-protected-resource/mcp` describes `/mcp`, and a resource indicator naming only a host is narrowed to that host's `/mcp` at mint time (`auth::routes::resource_audience`). The 401 from `/mcp` carries `resource_metadata=`. `tests/mcp_oauth_flow.rs` walks the whole flow the way a client does.
- **Realms.** An identity is a principal on one host (`users.realm`, `user_repository::realm_authorizes_host`), recorded at creation from the sign-in host and not moved by signing in elsewhere; `*` means every host. Two things set it: an administrator (`set_user_realm`), and `auth.bootstrap_admins`, whose accounts get `*` on every sign-in — otherwise the account that exists to administer the engine would be scoped to whichever host it first touched, and the management host would refuse it. Self-registered identities never get `*`. Enforced in `SecureSessionManager::validate_session` and `refresh_session` rather than per-middleware, because a session token is accepted from a bearer header as readily as from a cookie. An empty realm authorizes nothing; the next sign-in fills it in.
- `auth/`: OAuth2/OIDC (Google, Microsoft, Apple under `auth/providers/`), PKCE, sessions, dynamic client registration, and local accounts.
  - **Federated login** is bound to the browser that started it (`auth/oauth_state.rs`): `/auth/login/{provider}` mints a 256-bit nonce, sends it as `state`, and keeps it — with the post-login redirect — in a host-only `HttpOnly` `SameSite=Lax` cookie; the callback is accepted only if the browser presents that nonce, which is then spent. Binding to the browser rather than the client address is deliberate: an address belongs to the network path, changes between IPv4 and IPv6 under Happy Eyeballs, and proves nothing. The cookie holds up to three pending logins, so a second tab does not invalidate the first.
  - **Local identities** (`auth/local.rs`, `[auth.internal]`, off by default): guests and username/password accounts in `local_credentials`, for solutions whose users should not hand over a real-world identity and for installs with no OAuth client. See `docs/INTERNAL_AUTH.md`. Every login path converges on `AuthManager::establish_session`, which reads roles from the repository rather than from the caller. `auth.internal.bootstrap_admin_usernames` (and `bootstrap_admins`) are applied on every sign-in (`apply_bootstrap_admin_username`), since an upsert preserves the roles on a row it finds and the account named usually exists already. `--grant-role` and `--set-password` are the break-glass equivalents: they need the database but no server. `--set-password` reads the password from standard input, never from an argument `ps` can see, and ends the account's sessions.
  - **`/auth/account`** is everything that can be done with a session in hand: password change or claim, recovery codes, sessions, delegations. Its forms carry a CSRF token bound to the session (`validate_token_for`), because an unbound one can be fetched from `/auth/login` by anybody.
  - **Recovery codes** (`auth.internal.allow_recovery_codes`) are the reset path local accounts otherwise lack, having no verified address. A set is ten codes of about 98 bits, stored as unsalted SHA-256 (engine-generated entropy, nothing to pre-compute, one indexed lookup to redeem). Issuing takes the current password, replaces the previous set, and is the one response that carries credentials in its body, so it renders a page rather than redirecting. Redeeming marks the code used in the same transaction that writes the password, ends every session, and signs the caller in. It is throttled per address and per account, but a password the engine would refuse does not spend the account's budget.
  - **Sessions** are listed and revoked from `/auth/account`. The listing never returns `sessions.session_id`, which _is_ the token; rows are named by the surrogate `sessions.id`, and the delete is scoped to the caller's `user_id` in the statement. A session with an audience is labelled an API token, and revoking it drops that audience's refresh tokens; "sign out everywhere else" drops all of them. The refresh middleware re-sends the cookie to slide its `Max-Age`, but never over a session cookie the handler wrote, and it appends rather than replacing the header, so a cookie a script route set survives.
  - **Throttling**: `login_local` is limited per IP and per account (`RateLimitKey::LoginFailure`, ten failures refilling one per five minutes), since a guess spread over a thousand addresses meets no per-IP wall. Only failures spend the budget, so nobody can lock someone else out.
  - **The cookie** is host-only (no `Domain` is ever written) and `SameSite=Lax`. `auth::host_scoped_cookie_name` adds the `__Host-` prefix whenever it is `Secure`, so the browser enforces host-only: cookies are scoped by domain suffix, and without the prefix a host serving solution scripts could set a domain-wide cookie a management host reads as its own. The prefix is dropped when not `Secure`, because a browser discards a `__Host-` cookie over plain HTTP. Lax rather than Strict, because Strict would withhold the session on the cross-site navigation an MCP client makes into `/auth/oauth2/authorize`.
- **OAuth2 authorization** (`/auth/oauth2/authorize`) is the gate on API credentials, since the token carries the user's roles and an audience. It refuses an unregistered `client_id`, a `redirect_uri` the client did not register (compared byte-for-byte, RFC 6749 §3.1.2.3), a request without PKCE or using `plain`, and a `resource` not naming the host the flow runs on. Refusals before the redirect URI is matched answer the browser; after, they go to the client as `error=`. Registration is open, so what proves anything is consent: `oauth_client_grants` records what a person approved per `(user, client)`, and a request wider than the grant returns to the consent page, whose CSRF token is bound to the user. Every authorization response — the error redirect as well as the code — carries `iss` (RFC 9207), named by `MetadataConfig::issuer_for_host`, since every configured host is its own authorization server (RFC 8414 §3.3). `oauth2_token` re-checks the client, the exact redirect URI and PKCE, and a confidential client's secret before consuming the code. Registration is unauthenticated by design and bounded by a per-address budget (`RateLimitKey::ClientRegistration`).
- **Refresh tokens** are a separate credential from the session they mint (`auth::refresh_tokens`, `oauth_refresh_tokens`): a hash of an opaque token bound to `(user, client, audience, scope)`, redeemed only at the token endpoint by its client, and single-use — redeeming issues the successor in the same family, and presenting a spent one revokes the family, since "the client retried" and "someone has a copy" look the same. Refreshing mints a _fresh_ session from the repository's roles and realm, so a revocation in between takes effect.
- **Session binding** (`SecureSessionManager::check_binding`, on validation and refresh): a browser cookie is pinned to its User-Agent; a session with an audience is an API token whose client legitimately changes between token exchange and API calls, so it is bound by audience and realm instead. The address is advisory unless `security.strict_ip_validation` is on, which is meaningful only because `trusted_proxies` establishes the address from the connection.
- **Sessions carry the roles and realm they were minted with**, so anything that changes what an account may do calls `security::delete_sessions_for_user`: `update_user_roles`, `set_user_realm`, `delete_user`, `AuthManager::change_local_password`. It drops refresh tokens and delegations too.
- `revisions.rs`: every write to a script records what the script consisted of once the write landed, as a full manifest of `(path, digest)`. Content is addressed by digest and shared (`asset_blobs`), so a revision whose one module changed costs one blob and a row per file; digests are computed by Postgres and bytes copied blob-side, so no content crosses this process. The unit is the script, not the file, because that is the unit a change has; per-file history is a query over manifests (`file_history`), and the reverse would not be reconstructable. Numbering is serialised per script with `pg_advisory_xact_lock(hashtext(script_uri))`, and `record` joins the caller's transaction, so a rolled-back `transaction()` leaves no revision. `init_ok` is three-valued: `None` until the write path reports an outcome, since an `init()` that has not run has not failed; `last_good` — the newest revision that initialised — is the floor `revert_script` lands on. Retention under `[revisions]` needs _both_ clauses (older than `retention_days` _and_ outside the newest `keep_per_script`), because either alone deletes history someone may be using. Three things survive any policy: a labelled revision, the newest that initialised, and each script's newest; a pinned revision is excluded by the policy rather than left to the foreign key, which would refuse the whole statement. Blobs are collected in a second pass (`FOR UPDATE SKIP LOCKED`) outside `blob_grace_secs`. Operations: `list_revisions`, `diff_revisions`, `label_revision`, `revert_script`.
- `source_view.rs`: where a build reads a script's files from, as a parameter. `Live` is head (what an unpinned script serves), `Revision(n)` is what a revision held, and `Overlay` is files existing only for this request, laid over either — so a candidate change can be checked or tested before it is written, against the version it was written for. An overlay is a map of entries rather than files because `OverlayEntry::Deleted` matters: a check that kept reading a deleted module would pass a program that cannot be built. `cache_key` digests an overlay's sorted contents, so identical candidates share a cache entry; `is_live` keeps invalidation honest, since only the live view can change under a cache. `list_paths` lists paths, not content, because its caller is test discovery. `module_loader.rs` includes the view in its cache key, so a program built from a revision and the serving program coexist.
- `deployments.rs`: what a script serves when that is not its newest revision. Writes record revisions and advance head; a pin (`deploy_script`) makes them stop being deployments, so an agent can edit modules other people use without every experiment reaching production. No pin means follow head. Pins live in `script_deployments` and are cached per process (`deployments::pinned`), because every build reads them — and because an instance that has not yet heard of a pin should behave the way it believes. `load_pins` runs before any script executes, and `notifications.rs` refreshes peers. `serving_revision` — the pin, else head — is what an `init()` outcome and every log line are attributed to; a pinned script's head has not executed and must not be credited with an outcome. `deploy` refuses a revision that does not exist; "newest" is resolved to a number first, since a pin is meant to stop moving. Unpinning is a decision to stop deciding, so it re-initialises the script. `serving_view` answers `SourceView::Revision` for a pinned script, which is why pinning needs no second build path. Operations: `deploy_script`, `get_deployment`.
- `git_sync.rs` / `git_github.rs` / `git_credentials.rs`: a solution moving between an engine and a GitHub repository, in both directions. See `docs/GIT_SYNC.md`.
  - **Nothing touches local disk.** `libgit2` and `gix` want an on-disk object store, and the engine wants a _tree at a ref_, never history: a pull is one gzipped tar over HTTPS; a push is blobs, a tree, a commit and a ref move. Everything goes through `http_client::HttpClient`, since a repository URL is caller-supplied and needs the same URL and DNS validation as `fetch`.
  - **The layout is the directory structure**, not a manifest. A manifest's payload would be identity and ownership, and neither can travel between engines; strip both and the directories already are the mapping, since file names and import specifiers are relative. A directory holding `main.{ts,js,tsx,jsx}` is one script; a repository with an entry at its root is itself one script, and that wins, so adding a folder does not change what a single-script repository means. Script names are slugs composed once (`MAPPING_VERSION` 3) — the directory, `{prefix}-{directory}`, or the repository name for a single-script repository — and the directory is recorded on `script_git_sync` (`repo_dir`), so a renamed script is still the one its repository writes.
  - **`.aiwebengineignore`**, not `.gitignore` (whose entries never reach the archive), says which committed files are not content, with gitignore's own semantics. Beneath it, a dotfile is never taken, because files are servable and a re-included `.env` is a credential leak.
  - **A pull is a sync**: a module deleted upstream is deleted here, in one transaction, one revision and one `init()` (`upsert_assets_synced`). It writes as the caller, and is refused _whole_ rather than in part. It refuses a target that exists and this repository did not write, since owning a script is not agreeing that a repository may replace it.
  - **A push preserves what the script does not own** — README, CI workflow, ignored files — by the same predicate a pull uses, so the two cannot disagree. Blob ids are computed locally, so unchanged files are not uploaded and an unchanged script makes no commit. Divergence is reported, never merged, and `force` waives only this engine's check: `update_ref` never forces, so GitHub's fast-forward refusal stands.
  - **Credentials** are per user in `user_git_credentials`, encrypted under `security.secret_encryption_key`, and deliberately not in `user_secrets`, which is the JavaScript `secretStorage` and would be readable by the script it is keyed to. An engine with no key refuses to store one. Both directions are audited (push at High) and spend `RateLimitKey::GitSync`. GitHub only, and nothing unattended — no scheduled pulls, no webhooks — so the credential always belongs to somebody present.
- `log_retention.rs`: under `[logs]`, either the per-script count or the age alone removes a line — the opposite of revisions, because a log line is a diagnostic, not history. Recency is by `logs.seq`, not `created_at`, since two lines in one microsecond tie on the timestamp and a count-based cut would keep a different set each pass. `spawn_pruner` takes `pg_try_advisory_xact_lock`, so one instance does the work per tick. Clearing logs (`clear_logs`) is per script and takes ownership or an administrator.
- `scheduler/`: cron-like jobs scripts register; a background worker started beside the HTTP server and stopped by the same shutdown channel. A job gets `javascript.job_timeout_ms`, and the worker holds its claim through `lease.rs`, renewed for as long as the run lasts — a claim sized to the budget cannot work, because the wait for an execution slot comes after the claim and is unbounded, and a lapsed claim gets the row re-claimed so the finishing worker's update matches nothing. A failed one-off is retried on a widening delay and given up after five attempts.
- `tasks.rs`: the durable queue, deliberately not a relaxation of the scheduler. A scheduler job is a _declaration_ — `UNIQUE(script_uri, job_key)`, wiped before every `init()`, no payload. A task exists because something happened, carries what happened, survives `init()`, is enqueueable from any phase, and dies only with its script. It runs in script context on the job budget. Success deletes the row (the script's log has it under the run's invocation id); failure keeps it with `last_error`.
  - **Lanes**: at most one running task per `(script, lane)`, so work sharing state is serialised by the queue rather than by each caller. `personalTasks` defaults the lane to the person; `scriptTasks` defaults to none. Holding that takes three pieces of the claim: a `NOT EXISTS` excluding a lane with a _live_ run (live rather than `running`, so a dead worker's row stops blocking when its lease lapses); a `ROW_NUMBER` cutting a batch to one task per lane; and `pg_try_advisory_xact_lock(hashtext(script), hashtext(lane))` across workers. Because a statement's snapshot under `READ COMMITTED` may predate another worker's committed claim, claiming is two statements in one transaction: choose rows and lock their lanes, then re-check each lane under a fresh snapshot and claim what survives.
  - `scriptTasks` goes through `tasks_prelude.js`; `list_tasks` / `cancel_task` are the operations. See `docs/SCRIPT_TASKS.md`.
- `script_limits.rs`: what one script may spend when it differs from the engine-wide `[javascript]` budgets, so one agent can wait out a model call without every route handler getting the same ceiling — and, more often, so a script holding execution slots can be contained without a restart. Every field is optional (absent follows the engine); setting replaces rather than merges, so the row always states everything in force. Values are clamped rather than refused, because a stored value takes effect without a restart. Setting and reading take an administrator rather than ownership: this is a claim on slots, threads and memory shared with every tenant. Cached per instance, loaded before any script runs, refreshed through `notifications.rs`. Operations: `set_script_limits`, `get_script_limits`. See `docs/SCRIPT_LIMITS.md`.
- `sandbox.rs`: running part of a script with fewer capabilities than it holds — model-authored code with a chosen subset, or a planning turn that holds the reads and none of the writes, enforced beneath the JavaScript rather than requested in a prompt.
  - It is a **sub-execution**, not a mask: a restricted region sharing an object graph with its parent could be handed a function and call it, a capability leak by reference no mask catches. Separate contexts pass only JSON, so what may be reached is fixed when the globals are installed.
  - Nesting reuses what exists: a nested runtime's budget is clamped to the parent's remaining time (`within_host_budget`), and a nested transaction becomes a `SAVEPOINT`. `DepthGuard` bounds depth to four, since the shared budget bounds how long a chain runs but not how deep.
  - `narrow` refuses a subset the caller does not hold and an unknown name, rather than dropping either. `UserContext::attenuated` is an intersection, so no order of calls widens anything. The identity carries through — ownership, `personalStorage` and `{{secret:...}}` resolve against the same account.
  - A request-level mistake throws; what the _code_ did returns, because code that did not work is the result of the turn, not a failure of the loop.
  - **`hosts`** (`NetworkScope`) is the dimension a capability cannot express: exfiltration needs no write capability, so a planning turn holding only reads could put what it read into a URL. An entry is a host or `*.example.com` (subdomains, not the parent); ports are not part of it. It is checked on every redirect hop and reaches `McpClient` too. It rides on `FetchOptions` in a `#[serde(skip)]` field, written by the engine from the `UserContext` after the caller's options are parsed, so the restricted party cannot lift it. Omitted means "wherever the caller could already go". It is not spelled as a capability (`use_network:host`), which would make every `has_capability` a parse.
  - Surface: `sandbox.run`, `sandbox.held`, `sandbox.hosts`, `sandbox.capabilities` (`sandbox_prelude.js`); no engine operation, since this narrows a script from inside itself. See `docs/CAPABILITY_ATTENUATION.md`.
- `delegation.rs`: what a person has authorised a script to do as them while they are away — the reason background work can act for somebody at all. See `docs/DELEGATION.md`.
  - **A grant, not a wider context**: per `(user, script)`, shaped after `oauth_client_grants`, with a fixed scope vocabulary where every name gates something, a mandatory expiry, and withdrawal on `/auth/account` beside the sessions. Nothing is carried in the task row: `resolve` re-reads the grant, its expiry and the account when the task runs.
  - **The tier defaults to `authenticated`** however much the person holds, since background work has no business authoring a solution by default. `Scope::Author` and `Scope::Administer` are the way past it, and never quietly: they must be ticked on a consent page that spells out what they mean, and `tier_for` grants them only as far as the account's own roles reach — a grant is consent, not a promotion. They are independent, and ticking `administer` on an ordinary account grants nothing rather than falling back to `author`.
  - **Nouns and a verb.** Scopes name _what_ a delegation reaches; `Scope::Write` is the verb. A noun is checked where the person's thing is reached (`allows_delegated`) and answers as though it were not there; the verb is a capability and refuses at the gate every caller meets. Reading is the floor — `authenticated` minus the writes, keeping `UseNetwork`, `ReadSecrets` (`Scope::Secrets` gates _this person's_ secrets, not the script's) and `ManageStreams` (how a background run reports back). `Write` adds `WriteScriptData`, `WriteStorage` and `EnqueueTasks`, so a read-only delegation cannot chain tasks. `WriteSecrets` is never delegated. A refusal is terminal, not retried.
  - **Channels.** A webhook from Telegram or Slack arrives with nobody signed in. A script must not be able to name a user id — anyone reaching the webhook could then start anybody's agent — so `script_channel_identities` records which sender a person accepts triggers from, and `personalTasks.enqueueFrom` names `{channel, identity}` for the engine to resolve (`delegation::resolve_channel`). `sender()` never answers with an account id, which would end up in a bot's logs or chat. The primary key `(script_uri, channel, identity)` makes resolution unambiguous, and a second claimant is refused rather than replacing the first. The channel is lower-cased and the identity is not.
  - **Linking takes an invitation** (`script_channel_link_tokens`): a URL naming the sender could be built by anybody for anybody, and linking someone else's id first would intercept their messages. A script mints a single-use fifteen-minute token in reply to a message and sends it into that chat, so reaching the consent page means being able to read that sender's messages. Reading a token does not spend it; consenting spends it in the statement that reads it, so two browsers cannot both bind; minting replaces any outstanding token for the sender. Unlinking needs no token.
  - `RateLimitKey::ChannelTrigger` bounds triggers per link — the one budget whose spender is chosen by whoever sent the message. Verifying that a message came from that sender (a webhook signature) is the script's job.
- `lease.rs`: one implementation of "keep this worker's claim alive while it works", shared by `scheduler_jobs` and `script_tasks`. Each table's renewal statement is a literal rather than an interpolated table name, since sqlx checks only literal queries.
- `http_client.rs`: `fetch`, and what one blocking host call returning a whole string cannot do. See `docs/FETCH_CONCURRENCY.md`.
  - `fetch_all` runs several requests at once on `std::thread` workers — the same `fetch` per request, with a `Copy` client, so validation, redirects and secret substitution cannot diverge. Answers are positional, a refusal fails one slot, and a batch past `MAX_PARALLEL_FETCHES` runs in waves. The execution budget is read on the calling thread and re-armed on each worker (`host_budget_remaining` + `bound_host_calls`), because each host call reads its deadline from a thread-local.
  - `fetch_streaming` hands back status and headers as they arrive and the body in pieces. It asks for `identity` encoding, since incremental decompression needs a decoder of its own and streaming endpoints are not compressed, and it holds back bytes that do not yet form whole characters. Open streams live in a thread-local registry, closed by the outermost `HostCallBudget::drop`; a read takes the stream out and puts it back, so a blocking read holds no `RefCell` borrow.
  - `FetchOptions::binary` returns a non-UTF-8 body as `bodyBase64`. It is an option rather than a field on every response because base64 costs a third again, and not a silent fallback because an empty string reads like a server that sent nothing. Without it, a binary body is refused with a message naming the option.
  - A request body is bytes inside the client, given as `body` (text), `bodyBase64` or `form`, at most one. `form` is a list of parts the engine encodes as `multipart/form-data`: the boundary must be in the `Content-Type` and in none of the parts, which a script writing a string cannot guarantee, so the engine builds both and refuses a caller's own `Content-Type`. Names are percent-encoded the way browsers do, and a part's `contentType` with a line break is refused. Bodies are not searched for secret templates.
  - None of it is an event loop: a host call still blocks the script.
- **Registrations are one kind of thing.** `RouteMetadata` carries a `RouteKind` — `Handler`, `File` or `Stream` — so a file route is a route whose target is a file, with `:param` and `/*` patterns, one host filter, one invalidation, and registrations rebuilt on every `init()` so one a script stops making disappears. A file route is keyed under the `ASSET` pseudo-method and a stream under `STREAM`, so neither shares a slot with a handler on the same path; `route_index::resolve` states the precedence — file, then stream, then handler. A stream answers `GET` only.
- `stream_registry.rs` keeps **connections**: where a stream is published is a registration, and connection state is created on first connect. `open_connection` checks `server.max_connections_per_stream` / `max_total_stream_connections` and inserts under one acquisition of the registry lock, returning the id it stored; `ConnectionGuard` closes by that id on `Drop`, because a client disconnect produces no event — axum drops the response body. A refused connection answers 503. The engine's own stream (`/engine/script_updates`) has no script behind it, so it is registered directly and listed by `engine_owned_streams`. A stream may take a customization function that authorizes a connection and returns filter criteria — the place per-resource authorization lives, since "may this person read this row" is a fact about the script's data.
- A file route takes an `authorize` function (`registerRoute(path, { file, authorize })`), so "signed-in users only" and "the person this file belongs to" are expressible without a handler. Omitting it serves the file to anyone. A callback that _throws_ does not serve the file — answering 500 is right when the guard is broken. The engine still moves the bytes, streamed rather than marshalled through JavaScript.
- `resource_access.rs`: the shape such a callback answers in, wherever the engine serves data without running a handler (a stream's connection, a file route); `js_engine::execute_authorization_function` is the one implementation both run through. `AccessDecision` is `Allow(criteria)` or `Deny { status, reason }`. Any 4xx is the script's to choose and a 5xx is not, because a refusal is not the server failing; an out-of-range status answers 403 with a warning. `reason` is trimmed to 200 characters, being a script-written string that reaches an unauthenticated reader. A throw means the callback failed.
- **A script's name is a slug and can change** (`slug.rs`). Every table naming a script references `scripts(uri)` with `ON UPDATE CASCADE` (except `logs`, because the engine files its own lines under `server`; `rename_script` moves those itself), so a rename is one `UPDATE`, re-keying the cache and re-initialising. Physical table names hash `scripts.id`, so a name a renamed script left can be reused without colliding on its tables. A slug is lower-case letters, digits, `-` and `_`, up to 64, not `core`/`server`/`engine`/`native`/`system`, checked where a script is created or renamed, never where it is stored; `slug::suggest` proposes one. Flat on purpose: `acme/shop` would be a path, and the engine has no mounts to give a prefix meaning.
- **A path is held by one script per host.** `route_index::build_index` ranks scripts by `scripts.created_at` (then URI), and the first claimant of a `(host, path, method)` keeps it; later registrations are not indexed and appear as `collisions` in `exposure_report`. `registerRoute` asks `route_index::refusal_for` first and returns `{ ok: false, reason }` naming the holder (`check_script` reports a `route-conflict` instead). `set_script_hosts` refuses a binding that would put one script's registration on top of another's. Matching is on the registered string, so `/t/:id` and `/t/:name` do not collide.
- `exposure.rs`: which of a script's files the world can reach, read off the tree rather than off an `init()` call. `public/` is served, `resources/` is an MCP resource, everything else is reachable only to the linker and the script. A convention rather than an `exposure` column, because a column would be invisible in a repository. A registration naming a file outside its directory is **refused**, so publishing a file means moving it, and a mistyped path cannot publish a credential. A refusal is returned, not thrown, so a script that gets one path wrong keeps its other registrations. `exposure_report` lists what was refused, per script and cleared on each `init()`; `unclassified` counts scripts whose `init()` _failed_, not ones without an `init()`.
- `engine_page.rs`: every HTML page the engine renders — sign-in, account, consent, delegation, elevation, permission, install — is `engine_page::document` (one centred card) served by `engine_page::response` (the nonce policy). The look is `assets/engine.css`, inlined under the nonce, since several of these pages appear when something has already failed and should not need a second request. The same bytes are at `/engine/engine.css` for scripts that want to match; its `--aw-*` properties are the stable contract. A new engine page goes through `document`. See `docs/ENGINE_STYLES.md`.
- `error.rs` / `error/app_error.rs`: `AppError`/`AppResult` across the crate; `error_to_response` in `lib.rs` turns them into HTTP responses.
- Multi-instance deployments coordinate through Postgres LISTEN/NOTIFY (`notifications.rs`) rather than a message bus; each instance has a generated server id (`notifications::generate_server_id`) used for notifications and `/engine/health/cluster`.

## Testing

- Integration tests are `tests/*.rs`, one file per concern, with helpers in `tests/common/mod.rs`. Unit tests sit beside the code in `src/**`, and many need a database.
- They are full-stack: real servers against Postgres, with no mocked repository, so a test that needs a database fails without one rather than skipping — a skip reports a test that never ran as passing.
- `DATABASE_URL` names a _server_. Each test process claims a numbered slot database (`aiwebengine_test_slot_N`) recreated from a migrated template, so every test starts from the schema alone and the database `cargo run` uses is never opened. `src/test_db.rs` lives in `src` because both suites need it — a `#[cfg(test)]` module cannot see `tests/` — and `tests/common/mod.rs` compiles the same file with `#[path]`. `common::test_config` / `common::test_pool` and `test_db::pool` / `test_db::connection_string_blocking` are the only ways to reach the database; anything else bypasses the isolation. The blocking accessors provision on a thread and runtime of their own, since a unit test may be a plain `#[test]` or a `#[tokio::test]` (where `Runtime::block_on` panics), and that runtime keeps the slot claim alive for the process. Slots are claimed with a session advisory lock, so the claim ends when the process's connection closes however the process ends. `AIWEBENGINE_TEST_DB_SHARED=1` opts out, to inspect what a failing test left.
- The isolation is what makes the suite deterministic: `execute_startup_scripts` runs every script in the database, so on a shared database a test's result would depend on what earlier tests left. Tests run in parallel with no retries; a test that passes only on retry is a race to fix.
- `cargo-nextest` is the runner (`make test`, `make check`, `make ci`). `cargo test` does not pass: it runs a binary's tests as threads in one process, each with its own `#[tokio::test]` runtime, while a shared pool is driven by whichever runtime opened it, so later tests block on its connections. nextest's process-per-test model gives each test one runtime and one pool.
