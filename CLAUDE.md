# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this project is

**aiwebengine** is a Rust application engine that lets "solution developers" write JavaScript/TypeScript scripts which are executed inside an embedded, sandboxed QuickJS runtime (via `rquickjs`). The Rust core handles HTTP (Axum), routing, GraphQL (async-graphql), MCP (Model Context Protocol), auth (OAuth2/OIDC + sessions), a PostgreSQL-backed script/asset repository, and a capability-based security sandbox around every JS global. Scripts register HTTP route handlers, GraphQL resolvers, scheduled jobs, and message listeners at runtime — there's no separate build step for scripts, they're stored in Postgres and (re)loaded dynamically.

## Common commands

```bash
# Build & run
cargo build --release
source .env && cargo run                    # requires config.toml (copy from config.local.toml) and .env (from .env.example)
make dev                                     # cargo-watch auto-reload
make dev-local                               # run with localhost OAuth redirect (http://localhost:3000)

# Tests
make test                                    # cargo-nextest run --all-features --no-fail-fast (preferred)
make test-simple                             # plain `cargo test --all-features`
cargo nextest run <test_name_substring>      # run a single test / filter by name
cargo nextest run --test <file_stem>         # run one integration test file, e.g. `cargo nextest run --test dispatcher`
make coverage                                # cargo llvm-cov --all-features --html -> target/llvm-cov/html/index.html

# Lint / format / typecheck
make lint                                    # cargo clippy --all-targets -- -D warnings, plus markdownlint
make format                                  # cargo fmt --all + prettier for md/js/ts
make format-check                            # cargo fmt --all -- --check (CI-safe, no writes)
make typecheck                               # npm run typecheck -> tsc against scripts/**/*.{js,ts,tsx} using tsconfig.typecheck.json
make check                                   # format-check + lint + typecheck + test-simple (run before committing)
make ci                                      # check + coverage

# Docker (Postgres is required; there's no in-memory fallback)
make docker-setup && make docker-prod        # first-time production-style setup
make docker-localhost                        # https://localhost, self-signed cert, no DNS needed
make postgres-local                          # start only Postgres for local `cargo run` development
```

Config files are environment-specific templates copied to `config.toml` (`config.local.toml` / `config.staging.toml` / `config.production.toml`), and are overridden via `APP_<SECTION>__<SUBSECTION>__<KEY>` env vars (figment). `cargo run -- --validate-config` validates config without starting the server.

## Architecture

### Request lifecycle

1. `main.rs` loads config (`config::AppConfig`), sets up tracing, then calls `start_server_with_config` in `lib.rs`.
2. `lib.rs::initialize_components` brings up the DB (`database.rs`), the global `repository::PostgresRepository` (`repository.rs`, ~7k lines — the source of truth for scripts, assets, logs, secrets, and script metadata), the Postgres LISTEN/NOTIFY-based `notifications.rs` (keeps a multi-instance cluster's script caches in sync), the `scheduler` module, and registers engine-provided streams (`engine_api::register_engine_streams`).
3. Every script is executed once at startup (`execute_startup_scripts`) to populate route/GraphQL/scheduler registrations, then each script's `init()` is invoked if present (`script_init.rs`).
4. Incoming HTTP requests that don't match a static Axum route are matched dynamically against script-registered routes: `find_route_handler` in `lib.rs` scans cached `registrations` on script metadata (populated by the script's `init()` call to `routeRegistry.registerRoute`), scored by specificity (exact > `:param` > `/*` wildcard).
5. Matched requests are dispatched into `js_engine::execute_script_secure` (or the streaming/GraphQL-specific variants), which spins up a fresh QuickJS `Runtime`/`Context`, injects the sandboxed globals, transpiles/bundles the script via `module_loader.rs` + `transpiler.rs` (TS/JSX → JS using `oxc`), and runs the named handler with a per-request `UserContext`.

### Security sandbox model

- Every JS global exposed to scripts goes through `security::secure_globals` (~4.5k lines) — it is the enforcement point, not `js_engine.rs`.
- Authorization is capability-based (`security::capabilities::Capability` + `UserContext`), not role-string checks. `UserContext::anonymous()/authenticated()/editor()/admin()` map to fixed capability sets built from the user's roles; anonymous callers get one fixed set — read scripts and assets, change nothing — with no mode that widens it. A `security.development_mode` flag (and an `AIWEBENGINE_MODE` env var that outranked it) used to hand that tier `AdministerEngine`, `WriteScripts` and the rest so a local instance could be driven without a login; it is gone, because administering an engine now takes being an administrator (`auth.internal.bootstrap_admin_usernames`, or `--grant-role` with no server running). Tests sign in as a fixed administrator through `tests/common`'s `AdminServer`, so the engine APIs are exercised through the middleware a deployment actually runs.
- The four tiers are distinct on purpose. **Authenticated** is someone _using_ a solution: a script serving a request runs under the requesting user's context, so this tier holds exactly what an ordinary request needs (`ReadScripts`, `ReadAssets`, `ViewLogs`, `ManageStreams`, `UseScriptDatabase`) and nothing that edits the solution. **Editor** adds authoring (`WriteScripts`, `DeleteScripts`, `WriteAssets`, `DeleteAssets`, `DeleteLogs`, `ManageGraphQL`, `ManageScriptDatabase`), always paired with an ownership check. **Administrator** adds `AdministerEngine`, the marker for acting on what you do not own — never test `DeleteScripts` as a proxy for "is an admin".
- All scripts are equal — there is no privileged/restricted split. Every script sees the same JS API surface, and each call is authorized against the _calling user_: their capabilities, whether they own the target script (`script_owners` table, `repository::user_owns_script`), and whether they hold the editor/administrator role (`user_repository::UserRole`). Engine administration (scripts, assets, users, secrets, logs, route introspection) is not exposed to JavaScript at all — it lives on the `/engine/*` HTTP endpoints and the engine MCP tools, where `engine_api` applies the same capability/ownership/admin rules.
- `security/headers.rs` is the layer that makes `security.enable_security_headers` and `security.content_security_policy` mean something — both were previously parsed and used by nothing. It fills in `X-Content-Type-Options`, `Referrer-Policy` and (over HTTPS only) `Strict-Transport-Security` on every response, and the configured CSP only on engine-owned paths (`engine_api::RESERVED_ROUTE_PREFIXES`) — a policy describes how a page is built and the engine can only speak for pages it wrote, so script responses get none and set their own. It never replaces a header the response already carries. Engine HTML pages carrying inline `<style>`/`<script>` set their own nonce policy first (`security::engine_page_policy`), which is why they survive `script-src 'self'`.
- `security/client_ip.rs` establishes which address a request came from, once, at the edge. `X-Forwarded-For` and `X-Real-IP` are read only when the connection itself came from a proxy named in `server.trusted_proxies` (addresses or CIDR networks, empty by default so nothing is believed), and the chain is walked right-to-left to the first hop that is not itself trusted — the leftmost entry is written by the client and is what made every rate-limit bucket and session fingerprint forgeable. `normalize_client_ip` is the outermost layer bar security headers: it rewrites the forwarding headers to the single address that survived, so middleware, handlers and scripts all read one already-judged value through `client_ip::from_headers`, which replaced four near-identical extractors. The socket address comes from `ConnectInfo`, which is why `lib.rs` serves with `into_make_service_with_connect_info`. The shipped Caddyfiles set `header_up X-Forwarded-For {remote_host}` so the proxy overwrites rather than appends.
- Other `security/` submodules: `csrf.rs`, `encryption.rs` (AES-GCM, used for sessions and at-rest secrets), `rate_limiting.rs`, `session.rs`, `audit.rs`, `threat_detection.rs`, `validation.rs`, `csp.rs`. Treat this whole directory as security-critical — changes here need extra scrutiny per `SECURITY.md`.

### JavaScript-facing API surface

- Script access is split into **script-internal** (only the script itself), **engine-internal** (any script in the same engine instance), and **external** (HTTP-exposed) — see README.md's API access model.
- There are no built-in engine scripts: all engine endpoints — script/asset management REST, user administration (`/engine/users`, `/engine/user_roles`), script host binding (`/engine/script_hosts`), cluster diagnostics (`/engine/health/cluster`), the script test runner (`/engine/run_tests`, also the `run_tests` MCP tool), the pre-deploy checker (`/engine/check` / `check_script`), the snippet evaluator (`/engine/eval` / `eval_script`) and the atomic multi-file asset write (`/engine/assets/batch` / `write_assets`), the engine MCP tools, `/engine/installed`, `/engine/openapi.json`, `/auth/unauthorized`, `/favicon.ico`, the `/engine/script_updates` stream and the log tail (`/engine/script_logs/stream`) — are implemented natively in Rust (`src/engine_api.rs`). Engine assets (favicon, type definitions) are compiled into the binary and served via the static-asset fallback in `repository::fetch_asset`. Ad hoc test fixtures live in `scripts/test_scripts/`. Example/demo solution scripts live in the separate [aiwebengine-examples](https://github.com/lpajunen/aiwebengine-examples) repo, not in this repo.
- TypeScript type declarations for the JS API are served dynamically at `/engine/types/v{version}/aiwebengine.d.ts` (referenced in `lib.rs`'s OpenAPI setup). `tsconfig.typecheck.json` + `assets/**/*.d.ts` are what `make typecheck` validates scripts against.
- `module_loader.rs` implements a minimal CommonJS-like bundler for asset-backed script imports (no dynamic `import()`); `transpiler.rs` handles TS/JSX/TSX transpilation via `oxc`.

### Multi-host serving

- `server.base_url` names the default host; `server.additional_base_urls` adds more. `hosts.rs` resolves a request's Host header onto one of them, falling back to the default for anything unrecognised (direct IP, dev machine, tunnel), so single-host deployments are unaffected.
- `server.management_hosts` restricts the management surface to the listed hosts; empty means all hosts. It covers every `/engine/*` endpoint except the static `/engine/installed` page, and the engine's _native_ MCP tools (`write_file`, `set_script_hosts`, `list_users`, …) on `/mcp`. Enforced in three places: a layer on the management router in `lib.rs`, a `/engine/` prefix check in `handle_dynamic_request` that covers the `/engine/script_updates` stream, and the `native_allowed` flag threaded into `mcp::list_tools_for_host` / `tool_is_available_on_host`. Matched against the raw Host header, not the canonicalised host, since a management host need not be one of the hosts scripts publish on.
- A script's registrations — HTTP routes, asset routes, streams, GraphQL operations, MCP tools — are published on the default host unless the `script_hosts` table binds it elsewhere; a `*` row means every configured host. Administrators change bindings via `/engine/script_hosts` or the `get_script_hosts`/`set_script_hosts` MCP tools.
- The route index is keyed by `(host, path, method)`, so two scripts can claim the same path on different hosts. Everything else filters through `route_index::script_serves_host` / `scripts_for_host`, which reuse the same cache and invalidation.

### Other core modules

- `graphql.rs` / `graphql_schema_gen.rs` / `graphql_ws.rs`: dynamic GraphQL schema built from script-registered resolvers (`async-graphql` dynamic-schema feature), rebuilt on demand; subscriptions available over WebSocket (`graphql-transport-ws`) and SSE (`/graphql/sse`).
- `mcp.rs` / `mcp_client.rs`: JSON-RPC 2.0 Model Context Protocol endpoint (`/mcp`) for AI tool integration, both as a server (exposing script-registered tools) and a client (`mcp_client.rs` for scripts calling out to other MCP servers). `/mcp` takes a Bearer token only, and only one carrying an audience for the host and path being requested (`security::session::resources_match`). Every token the OAuth2 endpoint issues gets one; a browser login gets none, so a session cookie is not an API credential — which matters because a bearer header discards the host scoping the cookie relied on. Both ends of that check have to name the resource the same way, and that is where it broke: a client builds the protected-resource document's URL out of the MCP server's URL (RFC 9728 §3.1), so `/.well-known/oauth-protected-resource/mcp` describes `/mcp` — answering with the bare origin sent every MCP client off to ask for a token whose audience `/mcp` then refused. A resource indicator naming only a host is narrowed to that host's `/mcp` at mint time (`auth::routes::resource_audience`), since several clients ask for the origin and `/mcp` is the only path an audience is ever checked on; the host is `hosts::resolved_host`, so a request arriving on an unconfigured name is compared against the host whose content it is actually served. The 401 from `/mcp` carries `resource_metadata=` pointing at that document. `tests/mcp_oauth_flow.rs` walks the whole flow the way a client does, because every piece of it had unit coverage while the flow itself did not work.
- Identities are scoped to a **realm**: the host an account is a principal on (`users.realm`, `user_repository::realm_authorizes_host`). Recorded at creation from the sign-in host and never moved by signing in elsewhere; `*` means every host. Two things set it: an administrator (`/engine/user_realm`, `set_user_realm` MCP tool), and an address the operator named in `auth.bootstrap_admins` — that account gets `*` on every sign-in, including one already stamped with a single host. Without that, the bootstrap path defeats itself on a multi-host deployment: the account that exists to administer the engine is scoped to whichever host it first touched, the management host refuses it, and the endpoint that would widen it is served only on the host it can no longer reach. Self-registered identities never get `*` — `upsert_internal_user` does not consult `bootstrap_admins` and guests and local accounts stay on their creating host. Enforced in `SecureSessionManager::validate_session` and `refresh_session` — at the bottom rather than per-middleware, because a session token is accepted from an `Authorization: Bearer` header as readily as from a cookie, and a bearer header carries none of the host scoping a browser applies. An empty realm predates the column and authorizes nothing; the next sign-in fills it in.
- `auth/`: OAuth2/OIDC (Google, Microsoft, Apple providers under `auth/providers/`), PKCE, session management, JWT, dynamic client registration — this is the "Phase 1/2" auth system referenced throughout the code. `auth/local.rs` adds identities the engine authenticates itself — guests (no credential) and username/password accounts in `local_credentials` — for solutions whose users should not have to hand over a real-world identity, and for personal installs with no OAuth client. Configured under `[auth.internal]`, which every shipped config template turns on; the code defaults are all `false`, so an engine whose config predates those fields behaves as though the feature were absent. See `docs/INTERNAL_AUTH.md`. `/auth/login` renders whichever of these is enabled as plain forms beside the OAuth buttons, and the four `/auth/guest` and `/auth/local/*` endpoints take JSON or form-encoded bodies, answering with JSON or a redirect to match — form submissions carry a CSRF token, JSON bodies do not need one. Every login path, federated or internal, converges on `AuthManager::establish_session`, which reads roles from the repository rather than from the caller. A personal install gets its owner from `auth.internal.bootstrap_admin_usernames` — the `bootstrap_admins` of an engine whose accounts have no provider-verified address — applied on every sign-in (`user_repository::apply_bootstrap_admin_username`) rather than only at creation, since an upsert preserves the roles on a row it finds and the account named is usually one that already exists; the same fix now covers `bootstrap_admins` naming an existing account. `aiwebengine --grant-role <username-or-email> administrator` is the break-glass equivalent: it needs the database but no running server, which is the only way back into an engine with no administrator left. `POST /auth/local/password` rotates a credential given the current one. `login_local` is throttled twice: per IP (`check_auth_rate_limit`) and per account (`RateLimitKey::LoginFailure`, ten wrong guesses refilling one per five minutes), because a guess spread across a thousand addresses meets no per-IP wall. Only failures spend the budget, so nobody can lock someone out of their own account by burning it for them. The session cookie is host-only — no `Set-Cookie` path writes a `Domain`, so each host keeps its own sign-in — and `auth::host_scoped_cookie_name` puts the `__Host-` prefix on the name whenever the cookie is `Secure`, which makes the browser enforce that rather than leaving it to every future handler. It matters on a multi-host deployment because cookies are scoped by domain suffix, not by origin: without the prefix a host serving solution scripts could set a domain-wide cookie that a management host reads as its own, and `SameSite` cannot help since every host under one registrable domain is the same site. The prefix is dropped when the cookie is not `Secure`, because a browser discards a `__Host-` cookie over plain HTTP and local development would lose sign-in altogether. `auth.cookie.domain` and `auth.cookie.same_site` are parsed and read by nothing — the cookie is host-only and `SameSite=Lax` unconditionally; Lax is deliberate, since `Strict` would withhold the session on the cross-site top-level navigation an MCP client makes into `/auth/oauth2/authorize` and force a re-login on every authorization.
- The OAuth2 authorization endpoint (`/auth/oauth2/authorize`) is the gate on API credentials, since the token it leads to carries the user's roles and an audience. It refuses a `client_id` that is not in `oauth_clients`, a `redirect_uri` that client did not register (compared byte-for-byte, per RFC 6749 §3.1.2.3), a request with no PKCE challenge or one using `plain`, and a `resource` that does not name the host the flow is running on. Refusals before the redirect URI is matched answer the browser; after it, they go back to the client as `error=`. Registration is open, so none of that proves who created a client — what does is consent: `oauth_client_grants` records what a person approved per `(user, client)`, and a request wider than the stored grant returns to the consent page. That form's CSRF token is bound to the user (`CsrfProtection::validate_token_for`), because an unbound token is one anybody can fetch from `/auth/login` with no browser and no account. `oauth2_token` re-checks all of it: the code belongs to the presenting client, the redirect URI matches exactly, PKCE is verified unconditionally, and a confidential client's secret is checked before the code is consumed. Registration itself is bounded only by a per-address budget (`RateLimitKey::ClientRegistration`, ten then one per ten minutes) — it is unauthenticated by design, since a client has no credential to present before it has one, so that budget is the only thing stopping a caller writing rows into `oauth_clients` in a loop.
- A refresh token is a separate credential from the session it mints (`auth::refresh_tokens`, `oauth_refresh_tokens`). The token endpoint used to return the session token in both `access_token` and `refresh_token`, which made rotation impossible and made a leaked refresh token a leaked access token carrying the same audience and roles. What is stored now is a hash of an opaque token bound to `(user, client, audience, scope)`: it authenticates nothing on its own, is redeemed only at the token endpoint by the client it was issued to, and is single-use — redeeming issues its successor in the same family, and presenting a spent one revokes the whole family, since "the client retried" and "someone else has a copy" are indistinguishable. Refreshing mints a _fresh_ session, re-reading roles and realm from the repository, so a revocation that happened in between takes effect rather than being copied forward; and `delete_sessions_for_user` drops the refresh tokens with the sessions, because otherwise the next refresh hands back the role that was just taken away.
- A session is bound to what it was minted against (`security::session::SecureSessionManager::check_binding`, run on validation _and_ refresh). A browser cookie is pinned to its User-Agent — a browser does not change it mid-session — while a session carrying an audience is an API token whose client legitimately differs between the token exchange and the API calls, so it is bound by audience and realm instead. The address is advisory by default (a phone changes networks) and binding when `security.strict_ip_validation` is on, which is worth having only because `server.trusted_proxies` establishes the address from the connection. What this replaced inverted itself: a User-Agent mismatch was forgiven for a caller whose User-Agent _said_ it was an editor or MCP client, and any mismatch at all was forgiven once the address had changed — so the more of the fingerprint differed, the more likely the session was accepted.
- Sessions carry the roles and realm they were minted with, so anything that changes what an account may do has to reach the sessions that already exist: `security::delete_sessions_for_user` is that statement, and `user_repository::update_user_roles`, `set_user_realm`, `delete_user` and `AuthManager::change_local_password` all make it. Without it, revoking an administrator revoked nothing they were holding until the session aged out — `max_session_age`, thirty days by default; narrowing a realm from `*` to one host left the same sessions authenticating everywhere for that long.
- `revisions.rs`: every write to a script — its root source or any of its assets — records what the script consisted of once the write landed. The record is a full manifest rather than a delta, and the content behind it is addressed by digest and shared (`asset_blobs`), so a revision of a script whose one module changed costs one blob and a row per file; the digests are computed by Postgres and the bytes copied blob-side, so no content crosses this process however large the tree. The unit is the script, not the file, because that is the unit a change actually has — assets are keyed by their owning script, one batch write already stores several in a transaction, and the changes worth undoing span modules; a per-file view is a query over the manifests (`file_history`) and the reverse is not reconstructable. Numbering is serialised per script with `pg_advisory_xact_lock(hashtext(script_uri))`, since two writes landing together would read the same `MAX(revision)` and one would fail the unique constraint, and `record` joins the caller's transaction when there is one, so a script writing inside `transaction()` that then rolls back leaves no revision describing content nobody can read. `init_ok` is three-valued on purpose: `None` until the write path reports an outcome, because an `init()` that has not run is not one that failed, and `last_good` — the newest revision that initialised cleanly — is the floor `revert_script` lands on. Retention under `[revisions]` requires _both_ clauses before anything goes, unlike `[logs]`: a revision has to be older than `retention_days` _and_ outside the newest `keep_per_script` of its script, because either alone deletes history someone is plausibly still using. Three things survive any policy — a labelled revision (someone said out loud that this one is worth returning to), the newest that initialised cleanly, and the newest revision of each script — and a revision pinned by `deployments.rs` is named by the policy rather than left to the foreign key, which would refuse the whole statement rather than the one row. Blobs are collected in a second pass after the revisions commit, opportunistically (`FOR UPDATE SKIP LOCKED`), so a collection that cannot run does not undo pruning that already succeeded; `blob_grace_secs` is the window a collector must not act inside, wide on purpose because an uncollected orphan costs one pass of waiting and collecting one too early costs a write its revision. Surface: `/engine/revisions`, `/engine/revisions/diff`, `/engine/revisions/label`, `/engine/revisions/revert`, and the `list_revisions` / `diff_revisions` / `label_revision` / `revert_script` MCP tools.
- `deployments.rs`: what a script serves, when that is not simply its newest revision. Writing a script's files used to _be_ deploying them — right for one person editing their own script, wrong as soon as an agent is editing modules other people are using, because every experiment reaches production for want of anywhere else to go. A pin separates the two: writes still record revisions and still advance head, they stop being deployments. No pin means follow head, which is what every script does until somebody opts in, so `serving_view` is the identity function for deployments that existed before this. Pins live in `script_deployments` and are cached in a process-local map (`deployments::pinned`), because a script's program is built against it on every build so it cannot be a query — and because it is the more accurate answer: an instance that has not yet heard about a pin set elsewhere is still serving what it was, and should behave the way it believes. `load_pins` runs at startup before any script executes, so an instance coming up does not briefly serve head, and `notifications.rs` drives `refresh` / `forget_pin` so peers pick up someone else's change. `serving_revision` — the pin, else head — is what attributes an `init()` outcome and every log line, and head is deliberately not the answer: a pinned script's head is a revision nothing has executed, and crediting it with an outcome it never earned turns `lastGood` into an assurance the engine cannot back. `deploy` refuses a revision that does not exist, and callers meaning "whatever is newest" resolve that to a number first, since the point of a pin is that it stops moving; `unpin` is not a deployment of head but a decision to stop deciding, so the caller re-initialises the script. `source_view.rs` is what makes a pin buildable at all — it turns "where does a build read files from" into a parameter (`Live`, `Revision`, `Overlay`), threaded through the module loader, whose caches key on it so a program built from a revision and the program serving requests can be cached side by side without displacing each other; that is also what lets `/engine/check` and the test runner work against a revision or an unstored candidate rather than only against what is deployed. Surface: `/engine/deploy` (POST to pin, DELETE to unpin, GET to report), and the `deploy_script` / `get_deployment` MCP tools.
- `log_retention.rs`: how much of a script's log survives, and the background pass that enforces it. Both dials under `[logs]` are enforced and either alone is enough to delete a line — a count per script leaves a thousand dormant scripts sitting on their full quota, an age window leaves one script logging in a loop to fill it — which is the opposite of `revisions::prune`, where a revision has to fall outside _both_ before it goes: a revision is history someone may still need, a log line is a diagnostic. Recency is by `logs.seq` rather than `created_at`, which is what `seq` exists for — two lines written in the same microsecond tie on the timestamp and the tie breaks differently on every query, so a count-based cut would keep a different hundred each pass — and it is what the log view orders by, so "the newest hundred" means the same hundred in both places. `spawn_pruner` mirrors `revisions::spawn_pruner` down to the `pg_try_advisory_xact_lock`, so one instance in a cluster does the work on any given tick. Before this the three settings under `[repository]` were parsed and read by nothing and the only prune was a manual engine action keeping a hardcoded twenty lines per script, so an unattended deployment grew the `logs` table forever. Deleting logs is now per-script only (`clear_logs` MCP tool, `DELETE /engine/script_logs?uri=`) and takes ownership or an administrator — the arm that took no `uri` let any holder of the editor-tier `DeleteLogs` truncate every script's logs in the engine, which is acting on what you do not own.
- `scheduler/`: cron-like job scheduling that scripts register into; runs as a background worker task started alongside the HTTP server (`scheduler::spawn_worker`) and shut down via the same graceful-shutdown channel.
- `stream_manager.rs` / `stream_registry.rs`: Server-Sent Events connection management for real-time script-driven streams, with optional per-stream customization functions (JS callbacks that filter/authorize connections).
- `dispatcher.rs`: pub/sub-style message dispatch between scripts (listeners registered by URI/handler, keyed by message type).
- `error.rs` / `error/app_error.rs`: unified `AppError`/`AppResult` used across the whole crate; `error_to_response` in `lib.rs` converts these into HTTP responses.
- Multi-instance deployments coordinate via Postgres LISTEN/NOTIFY (`notifications.rs`) rather than a separate message bus — each instance gets a generated server ID (`notifications::generate_server_id`) used for both notifications and `/engine/health/cluster` reporting.

### Testing

- Integration tests live in `tests/*.rs` (one file per concern: `dispatcher.rs`, `streaming.rs`, `security_capabilities.rs`, `security_sessions.rs`, `secrets.rs`, `openapi_validation.rs`, `http_fetch.rs`, `cluster.rs`, etc.) with shared helpers in `tests/common/mod.rs` and `tests/test_utils.rs`.
- These are full-stack tests that spin up real server instances against Postgres — there is no in-memory/mocked repository mode, so a running Postgres (e.g. via `make postgres-local`) is generally required to run the suite.
- `cargo-nextest` is the preferred runner (faster, better output); the `[profile.test]` in `Cargo.toml` trades some optimization for faster incremental test builds.

### Coding standards (from CONTRIBUTING.md)

- No `unwrap()`/`expect()` in production code — use `Result<T, E>` and the crate's `AppError`.
- Zero compiler warnings, zero clippy warnings (`cargo clippy --all-targets -- -D warnings` must pass clean).
- Conventional commit prefixes: `feat:`, `fix:`, `refactor:`, `test:`, `docs:`, `perf:`, `chore:`.
